# Guardrail controls: let mission rules decide

A mission manager writes rules for a mission in Studio, for example "do not contact a competitor" or "a person must approve each refund above 500 USD". A **rule checkpoint** is the moment when your agent asks Studio: "may I do this step?". Studio judges the step against the rules and answers **allow**, **pause** or **stop**.

## Rule checkpoint or human in the loop?

| | [Human in the loop](human-in-the-loop) | Rule checkpoint |
| --- | --- | --- |
| Who decides that a step waits | Your agent, in its code | The mission manager, with rules in Studio |
| Same for all missions | Yes | No, each mission has its own rules |
| What the person sees | The form of your agent | The decision screen of Studio |

Use both when you need both: your agent asks for the missing information, and the mission decides what is allowed.

## When to add it

Add a checkpoint to each step that has an effect outside your agent: it sends a message, calls a customer system, spends money, publishes or deletes. A step that only reads or computes does not need one.

## How it works

1. Your agent declares the checkpoint phases that it supports: `before` the effect, `after` it, or both.
2. When a mission has rules, Studio adds an opaque `rule_snapshot` to the `job.start` input.
3. Before the effect, your agent sends a checkpoint with the business facts of the step. Studio answers.
   - `allow`: do the effect.
   - `stop`: do not do it. The step fails. This is final.
   - `pause`: wait. A person decides in Studio, then Studio calls your `rule.checkpoint.resume` action with `allow` or `stop`.
4. After the effect, your agent can send a second checkpoint with the result.

Studio starts a job in a mission with rules only if the agent declares rule checkpoints.

:::note[Studio side]
The workspace needs a Rule Controller before a job in a mission with rules can start. [Set up rules](/docs/supervaize-fleet/rules/setup) explains how an admin configures it and writes the rules.
:::

## 1. Declare the capability

```python
registration = build_v2_agent_registration(
    agent_slug="my-agent",
    display_name="My Agent",
    a2ui_catalog_version="my-agent-ui.1",
    surfaces=["job.start", "case.step.awaiting"],
    actions=["job.start", "job.sync", "job.stop", "step.awaiting.submit"],
    rule_checkpoints={"phases": ["before", "after"]},
)
```

The SDK adds the `rule.checkpoint.resume` action to the registration. Register a handler for it (step 4).

## 2. Open the gate at job start

```python
from supervaizer import RuleCheckpointGate

GATES: dict[str, RuleCheckpointGate] = {}

def start_job(request: V2ActionRequest) -> dict:
    job_state = build_job_state(request)
    if "rule_snapshot" in request.input:  # the mission has rules
        GATES[request.job_id] = RuleCheckpointGate.from_job_start(account, request)
        hold_guarded_steps(job_state)     # set them to "pending": nothing has run yet
    JOBS[request.job_id] = job_state
    return started(job_state)
```

:::warning[Run the checkpoints after the start has answered]
Studio knows a case only after it received it in a job state. A checkpoint for a case that Studio does not know is refused. So return the guarded steps as `pending` from `job.start`, ask Studio for a sync, and run the checkpoints in `job.sync`.
:::

The `rule_snapshot` is opaque. Do not read it, change it, log it or copy it into case data.

## 3. Ask before and after the effect

```python
PAUSED = {"reason": "rule_checkpoint", "surface": "case.step.awaiting", "action": "rule.checkpoint.resume"}

async def run_guarded_step(gate: RuleCheckpointGate, job_id: str, case: dict, step: dict) -> None:
    ids = {"job_id": job_id, "case_id": case["id"], "step_id": step["id"]}

    decision = await gate.checkpoint(
        occurrence_id=step["id"], phase="before", **ids,
        context={"operation": "send_email", "recipient_domain": case["metadata"]["domain"]},
    )
    if decision.status == "pause":
        step["status"] = case["status"] = "awaiting"
        step["awaiting"] = dict(PAUSED)
        decision = await gate.wait_for_resume(decision, step["id"], "before", job_id=job_id, case_id=case["id"])
        step.pop("awaiting", None)
    if decision.status == "stop":
        step["status"] = case["status"] = "failed"
        return

    result = send_the_email(case)  # the effect runs only after an allow

    decision = await gate.checkpoint(
        occurrence_id=step["id"], phase="after", **ids,
        context={"operation": "send_email", "outcome": result.status},
    )
    step["status"] = case["status"] = "completed" if decision.status == "allow" else "failed"
```

- **`context`** holds the business facts that the rules judge: the operation, the amount, the recipient, the result. Use plain values. Do not send secrets.
- **`occurrence_id`** identifies this run of the step. Use a stable value, so a retry asks about the same occurrence.
- A paused step shows as `awaiting` with the reason `rule_checkpoint`. The person decides on Studio's guardrails screen, not in a form of your agent.

`wait_for_resume` waits inside your process. A real agent does not block a request on it: it returns the job state with the paused step and continues when the decision arrives. The Hello World file [`agent_rules.py`](https://github.com/runwaize/supervaize_hello_world/blob/main/agent_rules.py) shows this complete flow.

## 4. Receive the decision

```python
from supervaizer.contracts import RuleCheckpointResume
from supervaizer.rule_controls import resume_rule_checkpoint

@sv_server.v2_action("rule.checkpoint.resume", agent_slug=agent.slug)
async def resume(request: V2ActionRequest) -> dict:
    decision = RuleCheckpointResume.model_validate(
        request.input | {"job_id": request.job_id, "case_id": request.case_id, "agent_slug": request.agent_slug}
    )
    if resume_rule_checkpoint(decision) is None:  # no step of this process waits for it
        return {"status": "error", "effects": [{"type": "rule.checkpoint.rejected", "job_id": request.job_id,
                                                "message": "No checkpoint waits for this decision"}]}
    job_state = JOBS[request.job_id]
    return {"status": "ok",
            "effects": [{"type": "rule.checkpoint.resumed", "job_id": request.job_id}],
            "job_state": job_state}
```

`resume_rule_checkpoint` matches the decision to the waiting gate and wakes `wait_for_resume`. A decision for an unknown gate must fail: never apply it by guess.

## Keep the gate across restarts

The gate lives in memory in these examples. After a restart, the agent can no longer match a decision, and it must reject it. In production, store the `rule_snapshot` with your job and build the gate again from it.

The SDK also has a helper, `Case.run_guarded_step()`, that does the whole sequence and stores the result of each phase for a safe restart. See "Rule checkpoints" in the [SDK guide](https://github.com/supervaize/supervaizer/blob/main/docs/2026_05_SUPERVAIZER_v2.md#rule-checkpoints).

## Checklist

- [ ] `rule_checkpoints` lists the phases, and `rule.checkpoint.resume` has a handler.
- [ ] Every step with an outside effect asks `before`.
- [ ] The effect runs only after `allow`.
- [ ] `stop` fails the step and is final. `pause` shows the step as `awaiting`.
- [ ] The `context` has the facts a rule needs, and no secret.
- [ ] Jobs in a mission without rules run as before.
