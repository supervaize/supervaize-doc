The `supervaizer deploy` command builds your Supervaizer agent as a Docker image. It pushes the image to the registry of the platform and starts the service.

## Overview

:::info

The deployment CLI supports **three cloud platforms**:

- **GCP Cloud Run** - Serverless container platform
- **AWS App Runner** - Fully managed container service
- **DigitalOcean App Platform** - Container-based app hosting

:::

The workflow has five steps:

[<i className="bi bi-1-circle-fill"></i> **Test Locally** - Run your agent with Docker before you deploy](#local)

[<i className="bi bi-2-circle-fill"></i> **Plan** - Preview the changes](#plan)

[<i className="bi bi-3-circle-fill"></i> **Deploy** - Build, push, and deploy the service](#deploy)

[<i className="bi bi-4-circle-fill"></i> **Monitor** - Check the status and the health](#status)

[<i className="bi bi-5-circle-fill"></i> **Cleanup** - Remove the deployment](#down)

## Prerequisites

### Install the deploy extra

The deploy commands need the `deploy` extra of the package.

```bash
pip install "supervaizer[deploy]"
```

Run the commands in a directory that has a `pyproject.toml` file. A parent directory up to three levels above also works. Declare the Python dependencies of your agent in this file.

## Commands

### Plan Deployment {#plan}

Preview what the CLI will deploy:

```bash
# Plan deployment to GCP Cloud Run
supervaizer deploy plan --platform cloud-run --name my-agent --env prod

# Plan with more options
supervaizer deploy plan \
  --platform aws-app-runner \
  --name email-agent \
  --env staging \
  --region us-east-1 \
  --project-id my-aws-account
```

The command prints the platform, the region, and the target image. It also prints a table of actions with type, resource, action, and description.

### Deploy Application {#deploy}

Deploy your Supervaizer agent:

```bash
# Deploy to GCP Cloud Run
supervaizer deploy up --platform cloud-run --name my-agent

# Deploy with more options
supervaizer deploy up \
  --platform do-app-platform \
  --name email-agent \
  --env prod \
  --region nyc3 \
  --port 8000 \
  --generate-api-key \
  --generate-rsa
```

**Deployment Process:**

1. **Build** - Build the Docker image from your code.
2. **Push** - Push the image to the registry of the platform.
3. **Secrets** - Store the API keys as secrets of the platform.
4. **Deploy** - Create or update the service.
5. **Configure** - Set `SUPERVAIZER_PUBLIC_URL` to the service URL.
6. **Verify** - Check the health of the service.

The command prints the service URL, the documentation URLs, the revision, the status, and the health.

#### Image name

The `--image` option takes `name[:tag]`. The CLI adds the registry of the platform. A value with `/` is not valid.

The default image is `{name}-{env}:{git-sha}`.

| Platform        | Registry                            |
| --------------- | ----------------------------------- |
| `cloud-run`      | Artifact Registry of your project   |
| `aws-app-runner` | Amazon ECR of your account          |
| `do-app-platform` | Container registry of your account |

:::info[Credentials stay out of the image]

The CLI does not put credentials in the image. It gives them to the service at runtime.

:::

### Check Status {#status}

Check the status and the health of your deployment:

```bash
supervaizer deploy status --platform cloud-run --name my-agent --env prod
```

The command prints the local state from `.deployment/state.json`. It then prints the live status from the platform.

### Remove Deployment {#down}

Remove the service and its resources:

```bash
# Ask for confirmation
supervaizer deploy down --platform cloud-run --name my-agent --env prod

# Skip the confirmation
supervaizer deploy down --platform aws-app-runner --name email-agent --yes
```

**Cleanup Process:**

1. **Confirm** - The CLI asks for confirmation. The `--yes` option skips it.
2. **Delete** - The CLI deletes the service.
3. **Secrets** - On Cloud Run and AWS, the CLI deletes the secrets of the service.
4. **State** - The CLI removes the local deployment state.

:::warning[Registries]

On AWS, the command also deletes the ECR repository of the service. On Cloud Run and DigitalOcean, the images stay in the registry. DigitalOcean keeps the registry because the whole account shares it.

:::

### Test Locally {#local}

Test your agent with Docker before you deploy:

```bash
# Test locally with the default settings
supervaizer deploy local --name my-agent

# Test with more options
supervaizer deploy local \
  --name email-agent \
  --env dev \
  --port 8000 \
  --generate-api-key \
  --generate-rsa \
  --timeout 60 \
  --verbose
```

**Local Testing Process:**

1. **Docker Check** - Check that Docker runs.
2. **Secrets** - Set the test API key and the optional RSA key.
3. **Generate Files** - Create the Dockerfile, `docker-compose.yml`, and `.dockerignore`.
4. **Build Image** - Build the image with the `local-test` tag.
5. **Start** - Start the service with Docker Compose.
6. **Wait** - Wait for the service to answer.
7. **Health Check** - Call `/.well-known/health` and `/docs`.
8. **Display Info** - Show the service URL and the access information.

The command prints the service URL, the `/docs` URL, and the `/redoc` URL.

**Local Testing Options:**

| Option                | Description                                      | Default                  |
| --------------------- | ------------------------------------------------ | ------------------------ |
| `--name`              | Service base name (required, the CLI asks for it) | none                     |
| `--env`               | Environment (`dev`, `staging`, `prod`)           | `dev`                    |
| `--port`              | Application port                                 | `8000`                   |
| `--generate-api-key`  | Create a random API key for the test             | `false`                  |
| `--generate-rsa`      | Generate an RSA private key for the test         | `false`                  |
| `--timeout`           | Seconds to wait for the service                  | `300`                    |
| `--verbose`           | Show the Docker Compose output                   | `false`                  |
| `--docker-files-only` | Generate the Docker files and do not run them    | `false`                  |
| `--controller-file`   | Controller file name                             | `supervaizer_control.py` |

Without `--generate-api-key`, the test API key is `test-api-key-local`.

**Docker Files Only Mode:**

Use `--docker-files-only` to generate the Docker files and not start the services:

```bash
supervaizer deploy local --docker-files-only --name my-agent
```

This mode is useful for:

- **CI/CD pipelines** - Generate the files for an external Docker step
- **Custom Docker setups** - Use the files in your own workflow
- **File inspection** - Read the Dockerfile before you run it

**Generated Files:**

- `.deployment/Dockerfile` - Container image definition
- `.deployment/docker-compose.yml` - Service orchestration
- `.deployment/.dockerignore` - Docker build exclusions

The `docker-compose.yml` file holds secret values. The CLI sets its mode to `600`.

**Custom Controller File:**

Use `--controller-file` when your controller has another name:

```bash
supervaizer deploy local --controller-file my_controller.py
```

**Cleanup:**

```bash
# Stop the local services
docker compose -f .deployment/docker-compose.yml down

# Remove the generated files
supervaizer deploy clean
```

:::tip[Test first]

Local testing is fast. It does not need cloud authentication.

:::

### Clean Generated Files {#clean}

Remove the files in `.deployment/`:

```bash
# Remove everything, after confirmation
supervaizer deploy clean

# Skip the confirmation
supervaizer deploy clean --force

# Remove only the Docker files
supervaizer deploy clean --docker-only

# Remove only the deployment state
supervaizer deploy clean --state-only
```

You cannot use `--docker-only` and `--state-only` together. The `--verbose` option shows more detail.

## Configuration Options

### Common Options

| Option               | Description                                                                          | Default                                   |
| -------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------- |
| `--platform`         | Cloud platform (`cloud-run`, `aws-app-runner`, `do-app-platform`)                    | **required**                              |
| `--name`             | Service base name (required, the CLI asks for it)                                    | none                                      |
| `--env`              | Environment (`dev`, `staging`, `prod`)                                               | `dev`                                     |
| `--region`           | Provider region                                                                      | `us-central1`, `us-east-1`, or `nyc3`     |
| `--project-id`       | GCP project / AWS account / DO project                                               | none                                      |
| `--port`             | Application port (`up` and `local`)                                                  | `8000`                                    |
| `--image`            | Image `name[:tag]` (`up`)                                                            | `{name}-{env}:{git-sha}`                  |
| `--generate-api-key` | Create a secure API key (`up` and `local`)                                           | `false`                                   |
| `--generate-rsa`     | Generate an RSA private key (`up` and `local`)                                       | `false`                                   |
| `--timeout`          | Timeout in seconds (`up` and `local`)                                                | `300`                                     |
| `--yes`              | Skip the confirmation prompt (`down`)                                                | `false`                                   |

The region default depends on the platform: `us-central1` for `cloud-run`, `us-east-1` for `aws-app-runner`, and `nyc3` for `do-app-platform`.

## Environment Variables

The CLI sets these variables in the service.

### Standard Variables

| Variable                  | Value                                     | Description                         |
| ------------------------- | ----------------------------------------- | ----------------------------------- |
| `SUPERVAIZER_ENVIRONMENT` | `--env` value                             | Environment name                    |
| `SUPERVAIZER_HOST`        | `0.0.0.0`                                 | Bind to all interfaces              |
| `SUPERVAIZER_PORT`        | `--port` value                            | Application port                    |
| `SUPERVAIZER_LOG_LEVEL`   | Your shell value, or `INFO`               | Logging level                       |
| `SUPERVAIZER_PUBLIC_URL`  | Service URL                               | The CLI sets it after the deployment |

### Variables from your shell

The CLI copies these variables into the service when they are set in your shell:

- `SUPERVAIZE_API_KEY`
- `SUPERVAIZE_WORKSPACE_ID`
- `SUPERVAIZE_API_URL`
- `SUPERVAIZER_SERVER_ID`
- `SUPERVAIZER_WORKSPACE_AUTH_REQUIRED`
- `SUPERVAIZER_WORKSPACE_AUTH_ISSUER`
- `SUPERVAIZER_WORKSPACE_AUTH_AUDIENCE`
- `SUPERVAIZER_WORKSPACE_AUTH_PUBLIC_KEY`
- `SUPERVAIZER_WORKSPACE_AUTH_JWKS_URL`
- `SUPERVAIZER_WORKSPACE_AUTH_LEEWAY_SECONDS`

The command `supervaizer login` writes the `SUPERVAIZE_*` and `SUPERVAIZER_WORKSPACE_AUTH_*` variables to a file. See the [quickstart](quickstart). Load the file in your shell before you run `deploy up`.

### Secret Variables

| Variable                  | Source                                      | Description                         |
| ------------------------- | ------------------------------------------- | ----------------------------------- |
| `SUPERVAIZER_API_KEY`     | `--generate-api-key`                        | API key for the `/api` routes |
| `SUPERVAIZER_PRIVATE_KEY` | `--generate-rsa`                            | RSA key for encryption              |
| `SUPERVAIZE_API_KEY`      | Your shell                                  | Studio API key                      |

The CLI stores these values in the secret manager of the platform.

## Generated Files

The CLI writes its files in the `.deployment/` directory:

```
.deployment/
├── Dockerfile              # Generated Docker image
├── .dockerignore           # Docker ignore rules
├── docker-compose.yml      # Local testing
├── do-app-spec.yaml        # DigitalOcean app spec
├── state.json              # Deployment state
└── logs/                   # Deployment logs
```

:::info

The CLI adds `.deployment/` to `.gitignore`. The `docker-compose.yml` and `do-app-spec.yaml` files hold secret values and have mode `600`.

:::

## Admin Interface

The admin interface is at `/manage`. You can open it only from a Tailscale network. In local mode, loopback also works. A public service URL does not give access to it.

See the [Admin Documentation](ref/2025_08_ADMIN_README.md).

## Health Verification

The CLI checks the service at the `/.well-known/health` path:

```bash
curl https://your-service-url/.well-known/health
```

This route belongs to the A2A routes of the server. Enable A2A endpoints in your `Server`.

The CLI retries the check with increasing delays until the service answers or the timeout ends.

## Troubleshooting

### Common Issues

#### **Authentication Errors**

```bash
# GCP: Re-authenticate
gcloud auth login
gcloud auth application-default login

# AWS: Check credentials
aws sts get-caller-identity

# DigitalOcean: Re-authenticate
doctl auth init
```

#### **Permission Errors**

Make sure your account has the permissions for your platform. See [Prerequisites](#prerequisites).

#### **Docker Build Failures**

```bash
# Check that Docker runs
docker ps

# Read the generated Dockerfile
cat .deployment/Dockerfile
```

#### **Health Check Timeouts**

```bash
# Check the status
supervaizer deploy status --platform cloud-run --name my-agent

# Test the health endpoint
curl https://your-service-url/.well-known/health

# Increase the timeout
supervaizer deploy up --platform cloud-run --name my-agent --timeout 600
```

#### **DigitalOcean: No container registry**

Create the registry with `doctl registry create <registry-name>`. Then run the command again.

### Debug

Read the deployment state:

```bash
cat .deployment/state.json
```

## Best Practices

### Security

1. **API Keys** - Use `--generate-api-key` for production.
2. **Secrets** - Never commit secrets to version control.
3. **Permissions** - Use least-privilege IAM roles.
4. **Networking** - Configure VPC and firewall rules as needed.

### Performance

1. **Image Size** - Keep the Docker image small.
2. **Dependencies** - Declare only the dependencies that you need in `pyproject.toml`.
