# Supervaizer Integration skill

**Source**: [<i className="bi bi-github"></i> supervaizer/skills/supervaizer-integration](https://github.com/supervaize/supervaizer/tree/main/skills/supervaizer-integration)

This skill lets a coding agent (Claude Code, Cursor, Codex, Gemini CLI) connect your Python agent to Supervaize Studio. It does two things:

1. It **interviews you**, so that you decide what a mission, a job, a case and a step are for your agent.
2. It **builds the integration** from the guides of this site, one topic at a time, with tests.

The skill is released with the Supervaizer SDK, so it follows the current version.

:::tip[Key Principle]
The most important integration decision is **semantic mapping**, not syntax. If the Job/Case/Step mapping is wrong, the controller code may run but the Supervaize UI and telemetry will be misleading.
:::

## Before you start

- A Python agent project (Python 3.12 or later) that already works.
- A coding agent that can load skills.
- 30 minutes for the interview. Your answers decide what operators see in Studio.

## Install

In Claude Code:

```
/plugin marketplace add supervaize/supervaizer
/plugin install supervaizer-integration
```

With another coding agent, clone the [SDK repository](https://github.com/supervaize/supervaizer) and point the agent to `skills/supervaizer-integration/SKILL.md`.

## Use it

Open your agent project and ask:

```
Integrate this agent with Supervaize.
```

To add one capability to an agent that is already connected, name it:

```
Add a human approval before the agent sends an e-mail.
```

## What happens

| Stage | What the skill does | What you do |
| --- | --- | --- |
| **1. Read** | Reads your code: the entrypoint, the inputs, the loops, the outputs, the secrets, the calls with outside effects | Nothing |
| **2. Interview** | Asks its questions in rounds. Each question comes with a recommended answer and the reason from your code | Decide |
| **3. Record** | Writes your decisions to `integration_spec.json` and shows you the summary | Confirm |
| **4. Build** | Runs `supervaizer scaffold`, then builds one topic at a time from its guide, each with a test | Review |
| **5. Test and connect** | Runs the controller without Studio, then helps you connect it to your workspace | Set the credentials |

### The interview

The skill does not accept "it depends". It asks about your last real run, repeats your answer as an example, and asks again when the result would be useless to an operator. A round looks like this:

```
Round 2: the cases

Q1. What does the operator count when they ask "how many are done"?
    Recommended: one case per lead. run_batch() loops over `leads`
    and each lead ends with its own status.

Q2. Is the list of leads known when the job starts?
    Recommended: yes. The CSV is read before the loop.

Q3. When one lead fails, do the others continue?
    Recommended: yes. The loop catches the error and goes on.
```

The questions follow this order, and each answer opens the next ones:

1. **The job**: what one click starts, who starts it, how long it runs.
2. **The cases**: what the operator counts.
3. **The steps**: what can fail, cost money, produce an output, have an outside effect or need a person.
4. **The topics** that your answers opened (table below).

The interview continues during the build. When the code shows a point that nobody decided, the skill stops and asks.

## What it builds

| Topic | The skill brings it up | Guide |
| --- | --- | --- |
| Registration, start form, job state | Always | [Build your controller](/docs/supervaizer-controller/controller-setup) |
| Field definitions of the forms | Always | [Field definitions](/docs/supervaizer-controller/controller-setup#fields) |
| Parameters and secrets | When your code reads API keys or settings | [Agent parameters](/docs/supervaizer-controller/parameters) |
| Cost reporting | Always | [Cost reporting](/docs/supervaizer-controller/cost-reporting) |
| Human in the loop | When a step cannot be undone, can be unsure or needs a person | [Human in the loop](/docs/supervaizer-controller/human-in-the-loop) |
| Guardrail controls | For each step with an effect outside the agent | [Guardrail controls](/docs/supervaizer-controller/rule-checkpoints) |
| Shared resources | When jobs share data or operators must edit it | [Shared resources](/docs/supervaizer-controller/resources) |
| Configure screen | When a job needs setup on its page | [Job Configurator](/docs/supervaizer-controller/job-configurator) |
| Analytics dashboards | When the agent has numbers to follow | [Job and mission analytics](/docs/supervaizer-controller/job-analytics) |

You can decline a topic. The skill then says in its final report which topics it skipped.

## What you get

- `supervaizer_control.py`: the controller, created by `supervaizer scaffold` and completed.
- Handlers in a module of your project, and tests that call them as Studio does.
- `integration_spec.json`: the record of your decisions.
- A final report: the mapping, the surfaces and actions, the tests, and what is still to write.

## Tips

- Answer with real examples: "last Monday the job had 40 contacts and 3 failed".
- Think like the operator. They do not know your code. They want to see what is done, what waits and what failed.
- Start small. A good job, case and step mapping with costs is worth more than every option.
